# SyncCloud — releasing

**Read this before any release cut, any version bump, and before cutting a new maintenance line.**
The day-to-day working agreement is [`CLAUDE.md`](CLAUDE.md); this file is the part of it that only
matters at release time. The branch table — each line's live marker — stays in `CLAUDE.md`, because
sessions consult it before a cut.

**A cut is never automatic.** Pushes to `main` are, but a cut puts a tag, a GitHub release and a live
Pages article in public, and none of those can be taken back. Build the whole cut locally, then ask
him once before step 3 puts any of it on `origin`. The ask covers the cut as a unit, not each command.

---

## 1. Rules

- **The version bump is part of the release, not a follow-up.** Between `v0.10` and `v2.8` the
  version in `project.yml` never moved, so twenty-odd tagged releases installed an app calling itself
  **1.0 (build 1)** — in the Settings rail, in `~/sync-cloud.log`, and in Finder's Version column.
  Nothing failed, because nothing depends on the version; it was simply wrong for two years.
- **The notes are part of the release too.** v2.9 got as far as being tagged with none, because
  nothing said to write them.
- **Tags are two components** — `v2.9`, never `v2.9.0` — and the tag namespace is release-only.
  This must print nothing:
  ```sh
  git tag | grep -v '^v[0-9]*\.[0-9]*$'
  ```
- **Releases are tags on the line that owns them** — `v2.9` from `v2.x`, `v5.0` from `main`. Tags are
  never branched from, except once, when a new maintenance line is cut from a major's last tag (§5).

---

## 2. The version

### Where it lives

`project.yml` is the only source of truth. The shape (live numbers are in `CLAUDE.md`'s table):

```yaml
CFBundleShortVersionString: "<MAJOR>.<MINOR>-dev"   # the marketing version — what people see
CFBundleVersion: "<MAJOR × 100 + MINOR>"            # the build number — what Launch Services orders by
```

`MacApp/Info.plist` is **generated from it by xcodegen and tracked in git** — run `xcodegen` after
editing `project.yml` and commit both, or the tracked plist goes stale.

Two things read the version, both display-only. There is no version-keyed migration or comparison
anywhere, which is what makes changing it safe:

- the Settings rail — `Modules/Settings/Sources/Settings/SettingsLayout.swift`
- the launch breadcrumb in `~/sync-cloud.log` — `MacApp/SyncCloudApp.swift`

### Three copies that must move with it, in the same commit

They repeat the number instead of reading it, so nothing fails when they drift:

- `MacApp/Info.plist` — regenerated by xcodegen
- the `versionMarker` literal in `Modules/Settings/Tests/Settings/SettingsLayoutTests.swift` (§6)
- the branch table in `CLAUDE.md` — the only live number that file spells

The table is the one that gets missed: the v4.2 re-bump moved `project.yml` and the test literal but
left every line's table reading `4.1-dev` / `401`. Run this from the repo root; it prints nothing when
the table is right and names the offender when it is not:

```sh
# main's row is read from the WORKING TREE — the copy you are about to land, and during a cut the
# only one that is right. Maintenance rows come from origin, the only place they exist. Reading
# origin on BOTH sides reports "clean" all through a local bump, which is useless.
for l in main v5.x v4.x v3.x v2.x; do
  if [ "$l" = main ]; then m=$(grep -o '"[0-9.]*-dev"' project.yml | tr -d '"')
  else m=$(git show origin/$l:project.yml | grep -o '"[0-9.]*-dev"' | tr -d '"'); fi
  r=$(grep "^| \`$l\`" CLAUDE.md | grep -o '`[0-9.]*-dev`' | tr -d '`')
  [ "$m" = "$r" ] || echo "$l: table says $r, project.yml says $m"
done
```

### The marketing version

Between releases each tip carries a **pre-release marker** suffixed `-dev` for the version it is
heading toward: "this build is no release", without implying a distributed beta. A release drops the
suffix and the tip is re-bumped straight afterwards, so a plain number like `2.9` is only ever what
the tagged commit itself carries.

Non-numeric is deliberate and verified. SyncCloud is distributed directly, not through the App Store,
so `CFBundleShortVersionString` is a free-form display string. Measured on a real Release build:
Launch Services stores `3.0-dev` verbatim and Spotlight emits `kMDItemVersion = "3.0-dev"` (Finder's
Version column); Launch Services *orders* on `CFBundleVersion`, not on this string. The App Store's
1–3-integers rule would apply only on submission, and would mean dropping the suffix, nothing more.

### The build number

`CFBundleVersion` = **MAJOR × 100 + MINOR** — `2.9` → `209`, `2.10` → `210`, `3.0` → `300`.

- One integer, so it orders correctly under numeric *and* naive string comparison (`"2.10"` vs
  `"2.9"` does not).
- It increases across all lines at once, so a v4 build always outranks a v3.x one.
- It is derived, not a second thing to remember, and changes in the same edit as the marker. The
  `-dev` build shares it with the release it becomes — fine, because it identifies the version, not
  the build.
- **Keep MINOR under 100** or it stops being monotonic, and **MAJOR under 100** because past that the
  rail's version line wraps (§6). Both halves of the scheme are bounded.

## 3. The notes

They live in two places: `RELEASE_NOTES.md` (`main` carries the superset) and `docs/releases.html`
(**`main` only** — Pages serves `docs/` from `main`).

- **The badge flips at the cut, not when the notes are written.** Pages goes live the moment notes
  land, so an article carrying `latest` announces a release nobody can install. A draft lands as
  `<article class="rel draft">`, the previous release **keeps** `latest`, and `RELEASE_NOTES.md`
  gets `## <version> — DRAFT, not released`. `586333f8` is the v4.1 cut that did it right.
- **Audit every claim against the previous tag — one command per claim.** The rules, each with the
  release that produced it, are in [`docs/release-notes-audit.md`](docs/release-notes-audit.md).
  Step 1 below requires working through it. Nothing fails when the audit is skipped, which is
  exactly why it gets skipped, and the notes then ship claims the code does not support.

## 4. Cutting it

Work in a worktree as always ([`COMMIT.md`](COMMIT.md)). The examples cut `v2.9` from `v2.x`.

1. **Drop the suffix and publish the notes, in one commit.**
   - `project.yml`: `2.9-dev` → `2.9`. Leave `CFBundleVersion` alone — it is already `209`.
   - `RELEASE_NOTES.md`: the DRAFT heading and blockquote go.
   - `docs/releases.html`: the article loses `class="rel draft"`; its tag goes `draft` /
     "In development" → `latest`; the previous release trades `latest` for a theme tag; the footer
     goes `Changes so far: <prev>...main` → `Full changelog: <prev>...<new>`.
   - **Then work through [`docs/release-notes-audit.md`](docs/release-notes-audit.md) before you
     commit.** It converts the "Still to come" section, runs the draft-word grep (the markup list is
     not the whole set), and audits every claim. v4.3's flip got every marker right and still landed
     two "not released" sentences, so the live page carried a `Latest` badge over a lede reading
     "Not released yet" until a follow-up caught it.

2. **Regenerate and update the test marker.** Run `xcodegen`, and set `versionMarker` in
   `SettingsLayoutTests.swift` to the same string — that literal is what gives
   `theVersionLineFitsTheRailOnOneLine` something real to measure (§6). Run the table check (§2).

3. **Commit, ask, then land on the line and let CI go green for that SHA — and stay off the machine
   while it runs.** The self-hosted runner IS this Mac.
   - The v4.5 cut took three attempts on one SHA: attempts 1 and 2 failed while local `swift test`
     runs competed with the runner; attempt 3 went green with no code change, the machine quiet and
     load average down from 6.61 to 4.20. Both load-sensitive flake families in
     [`docs/flaky-tests.md`](docs/flaky-tests.md) — *"every gate parks at once, on the pool their
     releases need"* and *"a log assertion reading a window that has already rolled"* — manufacture
     exactly the reds that look like a bad release.
   - Before rerunning, check `uptime` and
     `gh api repos/agirish/sync-cloud/actions/runners --jq '.runners[].busy'`. Budget a rerun into
     the cut rather than reading the first red as a verdict. The discriminator: run the failing
     suites locally at the red SHA — sub-second green there against a ~12 s timeout on CI is load,
     not code.
   - **Then check the folder survey's ground truth actually ran** — a green run does not say.
     `FolderSurveyGroundTruthTests` is the only suite comparing the survey rules to a real tree, and
     it is gated on a live profile and an awake display, so it is routinely absent from a green run.
     `FolderSurveyGroundTruthGateTests` always runs and prints the verdict:
     ```sh
     gh run view <run-id> --log | grep '\[ground-truth\]'   # want: RAN — …
     ```
     A `SKIPPED` line names the gate that closed it. On CI it always reads `liveProfile is in
     SYNCCLOUD_SKIP_MACHINE_PINNED` — by design — so a RAN only happens locally, with the display
     **woken and held**: `caffeinate -u <cmd>` only prevents sleep, and a short `-t` expires during
     the rebuild before the gate reads it. Use `nohup caffeinate -u -t 1200 &`, run the suite, then
     `pkill` the hold. Not a reason to hold the cut on its own, but a reason not to believe the rules
     were checked against reality in it.

4. **Tag that exact commit and push the tag, then create the release with an explicit `--target`.**
   The tag goes first, so the release binds to a tag that already exists:
   ```sh
   git tag v2.9 <sha> && git push origin v2.9
   gh release create v2.9 --target v2.x \
     --title "v2.9 — <the lede, shortened>" --notes-file <body> --latest
   ```
   Without `--target`, `gh release create` stores the default branch (`main`) as `target_commitish`
   even when the tag is on `v2.x`; v2.9 shipped that way. Nothing public renders it, but it is wrong
   in the edit view and every API read, and invites "was this cut from main?". It is fixable after
   publishing — the API's "unused if the Git tag already exists" caveat governs tag *creation*, not
   the stored value:
   ```sh
   RID=$(gh release view v2.9 --json databaseId --jq .databaseId)
   gh api --method PATCH repos/agirish/sync-cloud/releases/$RID -f target_commitish=v2.x
   ```
   **Then re-verify the tag did not move** — the real risk in editing a published release:
   `gh api repos/agirish/sync-cloud/git/refs/tags/v2.9 --jq .object.sha` must be unchanged, and
   `git branch -r --contains <sha>` must still name `origin/v2.x` alone. Do not "correct" **v2.8**,
   whose release says `main` and is right: it was tagged before the `v2.x` split at `0f016480`.

5. **Re-bump the tip to the next marker, immediately, in its own commit.** After `v2.9`, `v2.x`
   becomes `2.10-dev` / `210`: same edit shape as step 1, plus `xcodegen`, the test marker and the
   `CLAUDE.md` table. Now, not next time.

6. **Install and confirm what the app reports.** Run the `install-sync-cloud` skill and check that
   the first line of `~/sync-cloud.log` names the version you just cut.

## 5. Cutting a new maintenance line

When the next major opens on `main`, the shipped major keeps a maintenance line, cut from its last
tag. **In the same commit that pushes the new branch:**

- add its row to the branch table in `CLAUDE.md`;
- add it to `branches:` in `.github/workflows/tests.yml` — `v3.x` once went untested because the
  workflow only named the older lines;
- re-bump its tip to the next marker (§4 step 5) — `v3.x` was cut from `v3.1` and left on
  `3.1` / `301` for eleven days;
- extend the table check's line list (§2) and the `git ls-remote` expectation in `CLAUDE.md` §1.

Pushing the new branch is a push to a maintenance line, so it needs his yes (`CLAUDE.md` §4).

## 6. The version line has a width budget

The rail's version line is the one thing a version bump can actually break.

- `SettingsRail` is **fixed-width (176 pt) and does not scroll**, and the line has no `lineLimit`, so
  an over-wide string wraps to a second row instead of clipping. At the sheet's floor size that row
  takes the Large text size over its opening, which has only 0.4 pt of margin.
- `Bundle.main` under `swift test` is the test host and carries **no** version, so the line never
  rendered in tests and every rail test was blind to it. `SettingsRail.versionText` is the seam that
  fixes that: the tests inject `versionMarker` and really lay the line out. **Keep that literal in
  step with `project.yml`** — the whole reason §4 step 2 exists.
- **The safe ceiling is 19 characters including the `SyncCloud ` prefix** (measured 2026-08-30). The
  column is 142 pt; `SyncCloud 10.10-dev` (19 characters) measures 136 pt, but
  `SyncCloud 100.10-dev` (20) measures 145 pt and **wraps**. The scheme is safe only while MAJOR
  stays below 100 — a two-character marker from trouble. The per-size table is in the test's doc
  comment.
- If a version gets long enough to matter, `theVersionLineFitsTheRailOnOneLine` fails and names the
  number. Do not widen the rail without re-measuring the tabs that share its opening.
